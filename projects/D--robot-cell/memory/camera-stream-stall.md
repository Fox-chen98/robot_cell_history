相机 Orbbec Gemini 335(fw 1.6.00, 经 5m 绿联有源 USB3 延长线带供电, 直插主机) 偶发"取帧 6s 未成→重启流自救"(视觉服务日志), 表现为上架识别偶尔 8~10s。

**2026-09-17 已排除**: 不是接头/线断(两天 Windows 无相机 USB 掉线重连事件); 不是供电(常接电源, 且重开流就好); 不是带宽/协商(conn=USB3.2); 电源方案里无 USB 选择性暂停项; 固件 1.8.10(2026-06-26) changelog 无 USB3 流中途停止的修复。
**静止实验(臂 home 不动, 每 5s 取一帧 10 分钟)**: 走视觉服务 1280 满配 2 次卡顿(8.4s/8.3s, 服务已跑 6h); 独立脚本 640 低带宽 0 / 1280@30 0 / 1280@15 0 → 带宽假说不成立, 样本太少。
**剩余嫌疑**: ①视觉服务进程跑久流退化 ②随机链路误码。
**用户决定**: 不再专门做实验, 出问题再分析。为此自救日志行已加 时刻 + 服务已运行时长(vision_server.py STATE.started_at, 提交 e552ca7)。

**Why:** 用户不想在没有证据的地方动刀(刷固件/换线/降分辩率会伤认脸与盘点精度)。
**How to apply:** 用户报"识别慢了"时, 读 blue-space robot_cell\logs\vision_service.log 里带时刻的自救行, 对照臂动作时刻与服务运行时长; 攒几次看规律。生产上若要降带宽, 用 1280 保分辩率降到 15fps(选流时按 fps 选, 现 _find_profile 不看 fps), 不降分辩率。相关 [[stocktake-design]] [[vision-exam-bank]]。

**2026-09-23 复盘日志(vision_service.log, 共 29 次)**: 带时刻的 15 次: 09-20×2(68h) / 09-21×9(18~25h, 10:38~10:55 连断 7 次) / 09-22×2(43~47h) / 09-23×2(70h)。
- **设备掉线(SDK 报 `Device is deactivated/disconnected`)共 3 次**: 日志第 205、2132 行(早期无时刻) + **09-20 15:09:56**(→ 视觉进程退出 → 看门狗 5s 拉起重连, 中断约 20s)。其余 26 次均为重启流自救成功。**⚠ 但 09-20 15:09 前后 Windows System/Kernel-PnP 日志均无设备移除事件 → 是 SDK 层以为断开, 系统层相机一直在, 不是物理 USB 掉线**(09-23 查证, 更正此前"掉到 USB 层"的说法)。
- 09-23 两次: 13:38:37(任务 26 识别中)、13:59:53(那一帧 8.54s), 均自救成功, 无掉线。
- 服务刚重启 18h 就断、19.5h 时 17 分钟连断 7 次 → **"跑久退化"基本排除**, 剩"链路偶发误码/掉线"(线材/有源延长线/USB 口)。
- ⚠ 我曾把 09-22 10:38 识别 8.6s、14:16 识别 10.5s 解释成"分割阈值降级二次分割", **实为断流(同时刻日志有自救行)** —— 识别慢先查这份日志再解释。
- **09-23 查今天两次(13:38 / 13:59)**: 臂均静止在 home(排除拽线); 与相机空闲时长无关(历史 111 次长空闲取帧只卡 3 次, 多数卡顿在连续取帧中); SDK 日志(robot_cell/Log/OrbbecSDK.log.txt, 仅 22 行, 末条 09-16)无记录; Windows System/Kernel-PnP/Application 无 USB 事件。**结论: 找不到确切根因, 但各层都无硬件报错 → 更像 Windows Media Foundation(UVC)取流通道偶发停住, 重启流即恢复; 线材/接口/供电嫌疑下降**。
- SDK 日志里 08-28 setXu failed、09-10/09-16 "缺少硬件资源 MFT 启动流式传输失败" 是别的进程与视觉服务抢相机时留下的, 与断流无关。
- 下一步候选(用户未定): ①调高 SDK 日志级别, 等下次卡顿抓底层证据; ②查 Orbbec SDK 在 Windows 的取流后端(MSMF / libusb)能否切换

**2026-09-23 找到疑似根因并已修(待真机观察)**: SDK 详细日志(Log/sdk_debug/)显示视觉服务实际流 = 彩色 1280x720 **@60fps** / 深度 1280x800 **@30fps**(`_find_profile` 不看帧率, 取到首个匹配 = 60)。后果: SDK 频报 Align "not depth frame found"(一半帧集缺深度); 按需取帧时输出队列 60/s 满丢。机制推断: 两路节奏错开时 6s 内凑不出完整帧集 = 卡顿, 重启流重新对齐即好(与"各层无硬件报错"吻合; 与 09-17 独立脚本 30fps 0 卡顿吻合)。
修: gemini335.py 两路锁 30fps + `pipeline.enable_frame_sync()` + `FULL_FRAME_REQUIRE`(提交 Mac 见 git log "锁同为 30 帧")。改后缺深度警告 0、满丢 360→3/6s; 画面亮度 -0.2%。相机封装 hardware/depth_camera 已纳入 Mac 仓库与 deploy_cell。
**2026-11-09 掉线一例已结案 = 人为碰掉电源**(相机和机械臂一起断电): SDK 详细日志 `Log/sdk_debug/` 搜 "usb device removed" 能看到真实 USB 移除/重插时刻(15:18:59 移除, 2 秒后重插), 同一秒控制器网段出现网络浏览器选举事件。暴露的软件缺口: 相机 USB 重插后视觉服务不会重新打开它, 要到下次取帧(本次 92 分钟后)才超时→崩溃→服务重启。查掉线先看这份 SDK 日志, 别只看 vision_service.log。
诊断保留: 取帧失败记原因/最后成功时刻/硬件时间戳, 卡顿时打印; 若修后仍卡, 日志会给出具体原因。**验收: 跑数天看 vision_service.log 是否还有"取帧6s未成"**。
