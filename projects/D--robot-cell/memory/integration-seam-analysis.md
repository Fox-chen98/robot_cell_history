**2026-09-01 链式停滞事故的协作教训**(shelf链两次无报警停滞, 根因=rpc_heartbeat断线stop, 详见docs/格口路径库生产日志.md):

1. **集成不是包装, 是架构动作**: 把验证过的单步用bash串起来时, 每条进程边界都是状态边界(连接断开/心跳消失/模式残留/沙盘姿态污染)。串链前必须专门问一遍"衔接处有什么隐性状态会变?" 单步各自全绿≠链绿。
2. **"没炸过"≠"结构没问题"**: 旧编排链(go_real等)带同样的雷, 只因人工/判卷间隔让雷落空。运气会伪装成验证。
3. **用户现场直觉优先采信**: 用户第一时间说"是不是连在一起的问题"/"无报警不像超限"/"去查API手册", 三连全对; AI先后误诊速度、加速度两轮才回到用户方向。现场观察(同一位置/弹YES/无报警)是最高优先级证据, 先顺着查, 别急着用最近改过的参数当替罪羊。
4. **黑匣子先备份再重跑**: 事故录制同名覆盖两次丢证据; run_real已加失败抢救(crash_*_时间戳), 其他录制类工具照此办理。

**Why:** 误诊代价=两轮真机事故复现+用户信任消耗; 而正确路径(听用户+查手册)半小时可达。
**How to apply:** 写编排脚本时列"衔接状态清单"(连接/心跳/控制器模式/沙盘姿态/环境变量)逐项过; 用户提出现场假设时先设计裁决实验而非辩护自己的最近改动。相关: [[slot-path-production]] [[read-script-before-advising]]
